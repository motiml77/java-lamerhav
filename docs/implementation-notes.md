# הערות מימוש — מפת הקוד לריבוי בתי ספר

מסמך נלווה ל־`multi-school-plan.md`. כאן נמצאות **נקודות העיגון המדויקות בקוד** —
מה בדיוק צריך להשתנות ואיפה. נכתב אחרי קריאה של `app.html` בקומיט `41a9bbf`.

> מספרי השורות נכונים ל־`41a9bbf`. אם הקובץ השתנה — לאתר לפי הטקסט, לא לפי המספר.

## 1. החדשות הטובות: שכבת הנתונים כבר מרוכזת

**כל 40 הקריאות ל־Firestore** באפליקציה נמצאות בתוך אובייקט אחד — `DataService`
(שורות 841–1547). אין ולו קריאה אחת ל־`db.collection(` מחוץ לשכבה הזו.

זה אומר שהמעבר להיררכיה `schools/{slug}/...` הוא שינוי **ממוקד ובר־אימות**:
מוסיפים פונקציית עזר אחת בראש `DataService`, ומחליפים בה את כל הקריאות.

```js
// בראש DataService — הפניה יחידה לכל נתוני בית הספר הנוכחי
const schoolRef = () => db.collection('schools').doc(SCHOOL_SLUG);
const col = (name) => schoolRef().collection(name);
```

אחר כך: `db.collection('classes')` → `col('classes')`, וכן הלאה.

**בדיקת שלמות אוטומטית** אחרי ההחלפה — חייבת להחזיר 0:

```bash
grep -c "db\.collection(" app.html      # מצופה: 0
grep -c "col('" app.html                # מצופה: 40
```

## 2. מלכודת: בדיקות "דלג על המורה" מקודדות קשיח

זו הנקודה **הכי מסוכנת** במעבר, ואם מפספסים אותה נוצר באג אמיתי.

בארבעה מקומות ב־`DataService` יש סינון של המורה מתוך רשימת התלמידות — עם
האימייל כתוב קשיח בקוד (לא דרך `EDITOR_EMAIL`):

| שורה | פונקציה | הקוד |
|---|---|---|
| 946 | `promoteAllStudents` | `if (d.email === 'motiml77@gmail.com') return;` |
| 986 | `graduateGrade` | `if (d.email === 'motiml77@gmail.com' \|\| d.graduated) return;` |
| 1021 | `gradeCounts` | `if (d.email === 'motiml77@gmail.com') return;` |
| 1038 | `loadAllStudents` | `if (data.email !== 'motiml77@gmail.com' && ...)` |

**מה יקרה אם לא נשנה:** בבית ספר של מורה אחר, המורה שלו **יופיע כתלמידה**
ברשימת התלמידות, בדוח הציונים ובספירות השכבה — ובמקביל, `motiml77` יסונן
מרשימות של בתי ספר שהוא בכלל לא שייך אליהם.

**התיקון:** להשוות ל־`school.teacherEmail` של בית הספר הנוכחי, לא לקבוע קשיח.

## 5. נכסים סטטיים — חייב תיקון לפני הניתוב

`app.html:31` טוען `<script src="codemirror-java.min.js">` — **נתיב יחסי**.

- בכתובת `/lamerhav` (בלי לוכסן בסוף) הדפדפן פותר ל־`/codemirror-java.min.js` ✓
- בכתובת `/lamerhav/` (**עם** לוכסן) הוא פותר ל־`/lamerhav/codemirror-java.min.js` ✗ — עורך הקוד לא ייטען

**התיקון:** להוסיף `<base href="/">` ב־`<head>`, וגם להפוך את הנתיב לאבסולוטי
(`/codemirror-java.min.js`). שני החגורות — כי זו תקלה שקטה שמשביתה את עורך הקוד
רק אצל מי שהקליד לוכסן.

זהו הנכס היחיד שנטען יחסית ב־`app.html`. כל שאר ה־`url(...)` בקובץ הם הפניות
פנימיות ל־SVG (`url(#grid)`, `url(#arrowhead)`) ולא מושפעים.

## 7. החלטת אבטחה: כמה מסמך בית הספר חשוף?

**הבעיה:** מסך הכניסה צריך להציג את שם בית הספר, ואת המסכים "לא נמצא"/"מושהה" —
**לפני** ההתחברות. אבל אותו מסמך מחזיק גם את `teacherEmail`.

**מה נבדק:**

| אפשרות | יתרון | חיסרון |
|---|---|---|
| א. מסמך אחד, קריאה ציבורית | מקור אמת אחד; אין סיכון לחוסר־סנכרון | אימייל המורה גלוי למי שיודע את ה־slug |
| ב. שני מסמכים (ציבורי + פרטי) | האימייל מוגן | **סיכון אמיתי:** שני מקורות ל־`status`; אם אחד נשאר "פעיל" — בית ספר מושהה ממשיך לעבוד |
| ג. תת־מסמך פרטי לאימייל | האימייל מוגן, `status` יחיד | כל לקוח תלמידה מנסה קריאה שנכשלת → שגיאות בקונסול + round-trip מיותר |

**ההחלטה: אפשרות א'**, עם הגנה משלימה:

```
allow get:  if true;             // צריך לדעת את ה-slug המדויק
allow list: if isSuperAdmin();   // אי אפשר לשלוף את רשימת כל בתי הספר
```

**נימוקים:**
1. **המצב היום גרוע יותר** — `motiml77@gmail.com` כתוב בתוך `app.html`, שהוא קובץ
   ציבורי לחלוטין. כלומר אימייל המורה כבר היום גלוי לכל אחד שפותח "צפה במקור".
2. **האימייל אינו סוד שמקנה גישה** — ההזדהות היא Google; ידיעת האימייל לא נותנת דבר.
3. **`list` חסום** — אי אפשר למפות את בתי הספר; צריך לנחש slug מדויק.
4. **החשוב מכל:** מקור אמת יחיד ל־`status`. באפשרות ב', חוסר־סנכרון בין שני
   מסמכים פירושו בית ספר שהושהה וממשיך לעבוד — וזו תקלת אבטחה חמורה בהרבה
   מחשיפת כתובת מייל.

## 8. השהיה — חייבת להיאכף בשרת

לא מספיק להסתיר מסכים בצד הלקוח. `isActive(school)` חייב להיכנס לכל כלל
ב־`firestore.rules` (ר' טיוטה מלאה בסעיף 6 של מסמך התכנון).

בדיקת קבלה: להשהות בית ספר, ואז לנסות לכתוב אליו ישירות מהקונסול של הדפדפן
בתור המורה של אותו בי"ס. **חייב להיכשל ב־permission-denied.**

## 9. עלות `get()` בחוקי האבטחה

כל בדיקת הרשאה קוראת את מסמך בית הספר — קריאה מחויבת. Firestore שומר אותה
ב־cache בתוך אותה בקשה, והעומס (עשרות תלמידות לבית ספר) זניח.

זו הדרך הנכונה **בלי backend**. החלופה (Custom Claims) מחייבת Cloud Functions,
שלא קיימות בפרויקט. אם אי־פעם זה יכאב — משדרגים אז, לא עכשיו.

## 10. סדר בדיקות קבלה (אחרי כל שלב)

1. מנהל ראשי נכנס ל־`/admin` → רואה את רשימת בתי הספר.
2. מורה של בי"ס א' נכנס ל־`/schoolA` → רואה את התוכן שלו, **ולא** מופיע כתלמידה.
3. אותו מורה נכנס ל־`/schoolB` → נחשב תלמידה רגילה (לא מורה), ולא רואה מחוונים.
4. תלמידה של בי"ס א' → רואה רק את התשובות שלה.
5. בי"ס מושהה → גם המורה חסום, גם בקריאה ישירה מהקונסול.
6. slug לא קיים → מסך "לא נמצא", בלי קריסה.
7. `/schoolA/` (עם לוכסן) → עורך הקוד נטען.

## לוח הניהול: מונים, סטטיסטיקה ופרסום

### רישום כניסות
`activity/{email__YYYY-MM-DD}` — מזהה המסמך עצמו מונע כפילות, ולכן אין צורך
בטרנזקציה ואין מה לנקות. בנוסף יש מנעול ב-localStorage (`<slug>:visit_<יום>`)
כך שרענון דף לא שולח בכלל בקשה לשרת. `schoolStats()` סופר 30 יום אחורה
עם `count()` בצד השרת, ונופל חזרה לספירת מסמכים אם ה-SDK ישן.

### פרסום
מסמך יחיד `platform_settings/ads` בשורש — נקרא בכל בתי הספר, נכתב רק ע"י
המנהל הראשי. הקריאה פתוחה גם ללא התחברות (אלו תמונות פרסום בלבד).

מבנה:
```
{ popup:  { enabled, image | imageUrl, link, alt },
  banner: { enabled, image | imageUrl, link, alt } }
```

התמונה נשמרת כרגע כ-Data URI דחוס (`compressImage`, רוחב 1200, איכות 0.82)
בתוך המסמך, כי Firebase Storage עדיין חסום על Spark — ראי `storage-plan.md`.
הרינדור (`adSrc`) מעדיף `imageUrl` על `image`, ולכן המעבר ל-Storage יהיה
כתיבת `imageUrl` במקום `image` — בלי שינוי בתצוגה.

החלון הקופץ מוצג פעם ביום למשתמשת (`<slug>:ad_popup_<יום>_<email>`) ורק אחרי
הכניסה לאתר, לא במסך ההתחברות. גובה התמונות מוגבל (68vh בקופץ, 300px בבאנר)
כדי שתמונה גבוהה מדי לא תשבש את העמוד.

### פריסה — זהירות
`.vercel/repo.json` בריפו מקושר לפרויקט **java-lamerhav** (הייצור).
`vercel deploy --prod` מתוך תיקיית הפרויקט יעלה לאתר החי, גם בענף manager.
לפריסת התצוגה המקדימה: `git archive manager` לתיקייה זמנית, `vercel link`
לפרויקט `java-manager-preview`, ורק אז `deploy --prod`.

## תוכן שיעור גלובלי — platform_lessons

שלוש שכבות, מהחזקה לחלשה:

1. `classes/{id}.lesson` — עמוד קורס שמורה בנתה לכיתה שלה
2. `platform_lessons/{topicKey}` — דריסה גלובלית של המנהל הראשי, לכל בתי הספר
3. `LEARN_LIBRARY` + `TOPIC_LESSONS` — התוכן המובנה בקוד

`TopicLearnSection` מקבל `globalLesson` ובוחר לפי הסדר הזה. המפתח הוא
`topicKeyOf(title)` — מזהה לטיני יציב, כך ששינוי שם הנושא לא מנתק את הדריסה.

בלוח הניהול (לשונית "תוכן גלובלי"), בחירת נושא פותחת את העורך **טעון מראש
בתוכן שמוצג באתר כרגע** — הדריסה הגלובלית אם קיימת, אחרת המובנה. כך אף פעם
לא עורכים "על ריק". "שחזור לתוכן המקורי" מוחק את מסמך הדריסה.

`sections` (מקטעי ההסבר הארוכים מ-`TOPIC_LESSONS`) נשמרים כמו שהם ואינם
נערכים בממשק — הם עוברים דרך הדריסה בלי שינוי.
