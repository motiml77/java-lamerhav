# תוכנית יישום — מסך כניסה אחיד לכל בתי הספר, עם זיהוי בית ספר אחרי ההתחברות

## 1. מה נכון היום (עובדות מהבדיקה בלבד)

**ניתוב וקביעת בית הספר**
- `SCHOOL_SLUG` נגזר מ-`location.pathname` בזמן טעינת הסקריפט, כ-`const`, לפני React ולפני Firebase Auth — `app.html:527` (תבנית ב-524, רשימת שמורים ב-523).
- `Root` מחליט לפי ה-URL בלבד: בלי slug ובלי `/manage` → `<App />` במצב legacy (`app.html:12808`); אחרת ה-useEffect קורא `schools/{SCHOOL_SLUG}.get()` (`app.html:12820`), ורק בסוף מציב `CURRENT_SCHOOL = gate.school` ומרנדר `<App school={gate.school} />` (`app.html:12859`, `app.html:12863`).
- ה-prop `school` מגיע ל-`App` (`app.html:7250`) אך אינו בשימוש כלל בגוף הרכיב — כל הצריכה היא של הגלובל `CURRENT_SCHOOL`. יש שתי כתיבות בלבד לגלובל: ההצהרה `app.html:540` וההשמה `app.html:12859`.
- מסך הכניסה חי **בתוך** `App`: `if (!user) return <LoginScreen .../>` — `app.html:8338`. כלומר כל מסך כניסה שקיים היום כבר יודע לאיזה בית ספר הוא שייך.

**מה משתנה בין כתובות לפני התחברות**
- `app.html:4746` — הכתובית: `settings.subtitle || name || "לימוד ותרגול Java לבגרות"`. זו **השורה היחידה** ב-`LoginScreen` (4737–4799) שקוראת מ-`CURRENT_SCHOOL`; כל השאר (לוגו 4743, כותרת 4745, כפתורים 4750/4755, hero 4770–4771, Typewriter 4775, כרטיסיות 4779, טקסט תחתון 4791) מחרוזות קשיחות, וכך גם `LoginAmbience` (4698) ו-`CodeRainCanvas` (4625).
- `app.html:12854` — מסך "מושהה" מדפיס `{gate.school.name}` לכל גולש אנונימי.
- `app.html:12846` — מסך "בית ספר לא נמצא" מדפיס את ה-slug ומחליף לגמרי את מסך הכניסה.
- `app.html:12838–12839` — מצב loading של השער: רקע `#070B16` וספינר בלבד, בלי `login-stage`. זהו הבדל תזמון/מראה בין `/app.html` (LoginScreen מיד) לבין `/slug` (ספינר → LoginScreen).
- `app.html:12832` — בכשל רשת/Firebase רק `lamerhav` מקבל `LEGACY_SCHOOL_FALLBACK` ונכנס; כל slug אחר מקבל `not-found`.
- `app.html:530–537` — `LEGACY_SCHOOL_FALLBACK` מקודד לתוך ה-bundle את `name` ואת `settings.subtitle` של למרחב.
- `IS_DEMO_SITE` (`app.html:4728`) נגזר מ-hostname ולא מ-slug — הוא אינו יוצר הבדל בין בתי ספר על אותו דומיין.

**אירוח**
- `vercel.json:5` — `/` → `/lamerhav` (307); `firebase.json:16–22` — אותו דבר ב-302. אין middleware, אין `api/`, ו-Auth הוא `Persistence.LOCAL` (`app.html:680`) — כלומר אין cookie, ולכן שכבת האירוח **אינה יכולה** לנתב לפי זהות.

**נתונים וזהות**
- מזהה מסמך המשתמשת: `email.replace(/[.@]/g,'_')` — `app.html:969`, **בלי** `toLowerCase()`. אותה נוסחה ב-993, 1002, 1011, 1339 (activity), 1391, 1576 ועוד. אין `uid` כמזהה מסמך בשום מקום (uid מופיע רק ב-`app.html:1295` כ-`customMetadata` להעלאות).
- אין שדה slug במסמך המשתמשת — השיוך קיים אך ורק בנתיב `schools/{slug}/users/{safeEmail}` (`app.html:973–983`).
- זהות המורה נגזרת מ-`schools/{slug}.teacherEmail`, לא מאוסף users — `app.html:541`, `app.html:547`; למורה בדרך כלל אין מסמך תחת `users`.
- `isEditor` מחושב בתוך `onAuthStateChanged` עם deps `[]` — `app.html:7455`; אם `CURRENT_SCHOOL` יהיה null באותו רגע, `currentTeacherEmail()` יחזיר את המנהל הראשי וכל מורה אחרת תסווג כתלמידה.
- `col()` (`app.html:910–912`) מנתב ל-`schools/{slug}/{name}` רק כש-slug קיים ו-`CURRENT_SCHOOL` אינו `__legacyFallback`; כש-slug הוא null — אוסף שורש.
- `lsKey` (`app.html:546`) ממרחב-שם את localStorage לפי ה-slug, ומשמש ב-1340, 3841, 3883, 7375, 7409, 8081, 8095, 9391 — כולל טיימר המבחן.
- `AIService` שולח `school: SCHOOL_SLUG || 'lamerhav'` ל-Worker — `app.html:1902`, `1926`, `1968`.
- אין `functions/` ואין Blaze (`docs/blaze-checklist.md:28–29`); Admin SDK כן קיים מקומית (`firebase-setup/seed.js:17`). אין `firestore.indexes.json`. ה-SDK הוא compat 10.7.1 (`app.html:26`) ותומך גם ב-collectionGroup וגם ב-claims.
- מיגרציה: שלב 5 בוצע (קומיט `2fe96e5`, 130 מסמכים, נכתב `schools/lamerhav`). שלב 6 — מחיקת אוספי השורש — **לא** בוצע.

**אבטחה — כן, קריאה חוצת-בתי-ספר אפשרית היום**
- `firestore.rules` (HEAD): `function isActiveUser(school) { return isSignedIn() && isActive(school); }` — שורות 213–215. אין בה שום השוואה בין המשתמשת לבין `school`. משמעות: **כל** חשבון Google מחובר עומד בתנאי עבור **כל** בית ספר פעיל.
- ששת אוספי התוכן נשענים עליה: `classes` (231), `questions` (235), `exam_settings` (239), `notifications` (247), `media` (252), `practice` (257). תלמידה של בית ספר A מריצה בקונסולה `db.collection('schools').doc('B').collection('classes').get()` ומקבלת את כל תוכנית הלימודים והמבחנים של B — כולל מערך `exams` עם השאלות (`app.html:950–955`).
- גם **כתיבה** חוצת-בתי-ספר: `users create` (277), `activity create` (265), `students create` במבחנים ובשיעורי בית (292, 309).
- אורקל אנונימי: `allow read: if canManage(school) || resource == null || (...)` — `resource == null` הוא דיסיונקט עצמאי, ללא `isSignedIn`, ב-`firestore.rules:290–291` ו-`307–308`. בשילוב עם מזהה שנגזר מהאימייל (`app.html:969`) מתקבלת שאילתה אנונימית "האם X הגישה מבחן Y ב-B".
- `schools/{school}` פתוח ל-`get: if true` ו-`list` למנהל בלבד — כלומר slug שנוחש חושף `name` ו-`teacherEmail` לכל אחד.
- אוספי השורש עדיין חיים וקריאים לכל מחובר: `classes` (41), `questions` (46), `exam_settings` (52), `media` (136), `practice` (155), וכן אורקלי `resource == null` ב-91 ו-113.
- **אזהרה תפעולית:** `firestore.rules` נערך במהלך הבדיקה (הקובץ גדל מ-352 ל-375 שורות) ובקובץ העבודה כבר הוחל תיקון חלקי: `isActiveUser` הוגדר מחדש כ-`isActive(school) && (isMember(school) || isSchoolTeacher(school))` עם `memberId()/isMember()` סביב 222–239, ו-`users create` נשען כעת על `canRegister(school)` (309–310). התיקון חלקי: `isMember` מבוסס `exists()` בלבד — בלי בדיקת `approved` ובלי מעבר לבדיקת נתיב — ולכן אורקלי `resource == null` נותרו (315, 332) והחברות ניתנת להשגה עצמית בקריאת API אחת. **כל מספרי השורות בסעיף זה מתייחסים ל-HEAD; לפני כל עריכה יש לקרוא מחדש את הקובץ הנוכחי.**

## 2. העיצוב הנבחר

### 2.1 העיקרון

הבעיה מתפרקת לשתי בעיות עצמאיות שאסור לערבב:

1. **"כל הכתובות מציגות מסך כניסה זהה"** — בעיית UI טהורה. היא נפתרת בהסרת שלוש תלויות ב-`CURRENT_SCHOOL`/slug מהמסכים שלפני ההתחברות. לא נדרש שום שינוי בנתונים, בחוקים או באירוח.
2. **"המערכת מזהה לאיזה בית ספר המשתמשת שייכת"** — בעיית ניתוב, ורלוונטית רק לכתובת שאין בה slug (השורש). בכתובת `/school2` התשובה כבר בכתובת, וההרשמה של משתמשת חדשה נשענת עליה.

לכן: **הכתובות הקיימות אינן משתנות כלל**. `/school2` ממשיך לרוץ בדיוק כמו היום — שער → `CURRENT_SCHOOL` → `App` — רק שמסך הכניסה שלו כבר לא מסגיר את זהות בית הספר. השורש `/` הופך לכתובת נוספת שבה ההתחברות קודמת לניתוב.

### 2.2 ההחלטה המרכזית: איך נפתר השיוך אחרי ההתחברות

**נבחר: אוסף שורש `user_schools/{emailKey}` עם מערך `schools`, כרמז ניתוב בלבד, ובעקבותיו ניווט מלא ל-`/{slug}`.**

- מפתח: `email.toLowerCase().trim().replace(/[.@]/g,'_')` — נרמול שחסר היום ב-`app.html:969`.
- מסמך: `{ email, schools: [{ slug, role: 'student'|'teacher' }], updatedAt }`. **מערך** ולא שדה יחיד, כי `docs/multi-school-plan.md:134` קובע במפורש שאותו חשבון Google בבית ספר אחר נרשם כתלמידה חדשה ומבודדת — כלומר היחס אינו 1:1. שדה יחיד היה נמחק ב-last-write-wins; מסמך-לכל-שיוך היה מונע תשובה בקריאה אחת.
- **תפקיד** נשמר ברשומה, כי מורה של בית ספר חדש אין לו מסמך `users` כלל (`createSchool` ב-`app.html:12167–12170` לא יוצר אחד), ומצד שני מורה ותיק כן עלול להחזיק מסמך `users` ישן (ומכאן הסינון ב-`app.html:1381`).
- **האינדקס לעולם אינו מקור הרשאה.** גם אם משתמשת תכתוב לעצמה slug זר, החוקים ב-`schools/{slug}` יעצרו אותה — אין לה מסמך חברות שם. זה חייב להיכתב כהערה בקובץ החוקים כדי שאיש לא יקצר דרכו בעתיד.

**ההכרעה השנייה, לא פחות חשובה: ניווט מלא במקום הזרקת slug לזיכרון.**
אחרי קריאת האינדקס מבצעים `location.replace('/' + slug)` — טעינת דף מלאה. **לא** הופכים את `SCHOOL_SLUG` ל-`let` ולא מזריקים `CURRENT_SCHOOL` באמצע סשן. הסיבות, כולן מדידות בקוד:
- `isEditor` מחושב פעם אחת ב-`onAuthStateChanged` עם deps `[]` (`app.html:7455`) ואינו מחושב מחדש — מורה שאינה המנהל הראשי הייתה מסווגת כתלמידה ונשלחת ל-`PendingApprovalScreen`.
- `col()` (`app.html:910`) עם slug ריק נופל לאוספי השורש; `saveUserProfile` (`app.html:985`) הייתה כותבת פרופיל תלמידה אמיתי ל-`/users` בשורש — כתיבה שהחוקים מתירים ולכן לא תיתפס כשגיאה.
- `lsKey` (`app.html:546`) משנה מרחב-שם באמצע הסשן; טיימר המבחן (`8081`, `8095`, `9391`) מאבד את זמן ההתחלה.
- `AIService` (`1902/1926/1968`) היה מייחס קריאות ל-`lamerhav`.

ניווט מלא משמר את האינווריאנטה הקיימת — `CURRENT_SCHOOL` מוצב לפני שנוצר `App` — בלי לגעת באף אחד מהמנגנונים האלה.

### 2.3 מה נדחה ולמה

| חלופה | למה נדחתה |
|---|---|
| **Custom claims** (slug בטוקן) | אין `functions/` ואין Blaze (`docs/blaze-checklist.md:28–29`); claim לנרשמת חדשה מחייב אוטומציה בצד שרת (כתיבה ידנית מ-Admin SDK מקומי אפשרית, אך אינה פתרון שוטף). בנוסף הטוקן מתרענן כשעה — השהיית בית ספר, שנאכפת היום מיידית דרך `isActive()`, הייתה מאבדת מיידיות. פתרון נכון לטווח ארוך, לא לעכשיו. |
| **`collectionGroup('users')`** | דורש אינדקס collection-group ידני שאינו בגרסה (אין `firestore.indexes.json`), ודורש `match /{path=**}/users/{uid}` — תבנית שמתאחדת באיחוד מתירני על פני **כל** בתי הספר בבת אחת. בתבנית הזו אין משתנה `school` ולכן אי אפשר לבדוק `isActive(school)`. בנוסף היא תופסת גם את `/users` בשורש, שם `parent.parent` הוא null. |
| **הפניה לפי זהות בשכבת האירוח** | בלתי אפשרי: אין middleware ואין cookie (`Persistence.LOCAL`, `app.html:680`); שתי פלטפורמות האירוח מכריעות לפי source/regex בלבד. |
| **מסך "בחר בית ספר" לפני ההתחברות** | חושף את רשימת בתי הספר ולא פותר דבר — `list` על `schools` חסום בכוונה למנהל הראשי. |
| **הסרת `LEGACY_SCHOOL_FALLBACK` בשלב זה** | הדגל `__legacyFallback` הוא בדיוק מה ש-`col()` בודק. הסרה או הזרמת slug בלי הדגל תעביר את למרחב לקרוא מ-`schools/lamerhav` — ותרוקן את האתר החי אם המיגרציה לא שלמה. |

## 3. תוכנית יישום מדורגת

כל שלב עומד בפני עצמו, ניתן לפריסה ולאימות בנפרד, ואפשר לעצור אחרי כל אחד מהם.

### שלב 1 — מסך כניסה זהה בכל כתובת (UI בלבד)
**קבצים:** `app.html` בלבד. **בלי** שינוי חוקים, נתונים או אירוח.

1. `app.html:4746` — להחליף את כל הביטוי במחרוזת קבועה `"לימוד ותרגול Java לבגרות"`. הפולבק כבר קיים באותה שורה, ולכן אין סיכון לאלמנט ריק ואורך הטקסט דומה.
2. `app.html:12854` — במסך "מושהה": `<p>בית הספר אינו פעיל כרגע.</p>` במקום `{gate.school.name} אינו פעיל כרגע.` הכותרת והמשפט הבא כבר גנריים.
3. `app.html:12844–12849` — מסך "לא נמצא": להסיר את הצגת ה-slug (12846). המלצה חזקה יותר: להחזיר במצב `not-found` את `LoginScreen` עצמו, ולדחות את ההודעה לשלב שאחרי ההתחברות — כך גם נעלמת הרגרסיה של `app.html:12832` (כשל Firebase ⇒ כל בית ספר מלבד למרחב רואה "לא נמצא" בעוד למרחב רואה מסך תקין).
4. `app.html:12838–12839` — להחליף את הספינר הריק ברקע `login-stage` או ב-`LoginScreen` עם כפתורים מושבתים, כדי שהמסך הראשון הנראה יהיה זהה גם ב-`/app.html` וגם ב-`/slug`.
5. אופציונלי: לרוקן את `name`/`settings.subtitle` מ-`LEGACY_SCHOOL_FALLBACK` (`app.html:530–537`) כדי שהמחרוזת לא תישלח לכל דפדפן — **בלי** לגעת ב-`slug` וב-`__legacyFallback`.
6. להשאיר במודע: `IS_DEMO_SITE` (`app.html:4728`), כפתורי הדמו (4750, 4792), `enterDemo` (7627), ושם בית הספר בכותרת הפנימית (8552, 8554) — כולם אחרי ההתחברות או תלויי hostname, לא תלויי בית ספר.
7. **לא לגעת** ב-`StudentNameScreen` (`app.html:4830`, `4846`): `schoolGrades()` חייב להישאר פר-בית-ספר, אחרת בית ספר עם שכבות אחרות יראה כפתורים שגויים.

**התוצאה:** המטרה שהמנהל ניסח מושגת במלואה עבור כל הכתובות הקיימות — בלי שום שינוי בהתנהגות, בהרשמה או בהרשאות.

### שלב 2 — סגירת הבידוד בחוקים (חובה לפני כל ניתוב צד-לקוח)
**קובץ:** `firestore.rules` + `scripts/rules-test.js`.
תחילה לקרוא את הקובץ הנוכחי ולהשלים את התיקון החלקי שכבר הוחל בו: להוסיף בדיקת `approved`, להחליף בדיקות תוכן בבדיקות נתיב, ולסלק את אורקלי `resource == null`. הקוד המלא בסעיף 4.
**מלכודת שחייבים לכבד:** מורה בית הספר נכנס היום לתוכן דרך `isActiveUser`, ואין לו מסמך `users`. לכן כל שש שורות הקריאה חייבות להסתיים ב-`|| canManage(school)` ולא ב-`|| isSuperAdmin()` כפי שהן היום.
**מלכודת שנייה:** `approved` חסר פירושו "מאושרת" בלקוח (`app.html:7484`, `1048` בודקים `!== false`), והשדה נכתב רק בהרשמה חדשה (`app.html:980–983`). כתיבת `.approved == true` ישיר תנעל כל תלמידה ותיקה של למרחב. לכן `.data.get('approved', true) == true`.

### שלב 3 — סגירת אוספי השורש (שלב 6 של תוכנית המיגרציה)
מיגרציית התוכן כבר בוצעה (`2fe96e5`), אבל השורש עדיין קיים וקריא לכל מחובר. כל עוד הוא חי, נפילה שקטה של `col()` לשורש היא **הצלחה** ולא שגיאת הרשאות — כלומר אין רשת ביטחון שתתפוס טעות ניתוב, ומשתמשת יכולה "להתקיים" בשני מקומות בעוד האינדקס ממפה רק אחד. לאמת ספירות מול `schools/lamerhav`, למחוק את אוספי השורש, ולהחליף את חוקי השורש ב-`allow read, write: if false` (כולל סילוק אורקלי `resource == null` ב-91 ו-113).

### שלב 4 — חוקי האינדקס ואז הסקריפט

## 4. חוקי Firestore — הקוד המדויק

> יש לקרוא את `firestore.rules` הנוכחי לפני ההחלה: הקובץ נערך במהלך הבדיקה ומספרי השורות מוסטים. הקוד למטה מחליף את `isActiveUser` ואת הבלוקים המפורטים.

**א. פונקציות עזר — ליד ההגדרות הקיימות של `isActive`/`canManage`:**

```
// מזהה מסמך החברות, נגזר מהטוקן. אין .lower() — app.html:969 אינו מלנקס,
// והוספת lower() כאן תנתק חשבון שהטוקן שלו מכיל אות גדולה.
function memberId() {
  return request.auth.token.email.replace('[.@]', '_');
}

function memberDoc(school) {
  return get(/databases/$(database)/documents/schools/$(school)/users/$(memberId()));
}

// חברה פעילה בבית הספר הזה. סדר ה-&& קריטי: get() על מסמך שאינו קיים
// מחזיר null, ו-null.data מפיל את ההערכה — לכן בדיקת ה-!= null מקדימה.
// approved עם ברירת מחדל true, כדי לשקף את סמנטיקת הלקוח (app.html:7484).
function isSchoolStudent(school) {
  return isSignedIn()
    && request.auth.token.email != null
    && isActive(school)
    && memberDoc(school) != null
    && memberDoc(school).data.get('approved', true) == true;
}

// bootstrap להרשמה בלבד: מחוברת בבית ספר פעיל, בלי דרישת חברות.
function canRegister(school) {
  return isSignedIn() && isActive(school);
}
```

**ב. ששת אוספי התוכן** (`classes`, `questions`, `exam_settings`, `notifications`, `media`, `practice`) — כל שורת קריאה:

```
allow read: if isSchoolStudent(school) || canManage(school);
```

`canManage` ולא `isSuperAdmin` — אחרת מורה בית הספר עצמו נחסם מהתוכן שלו.

**ג. `schools/{school}/users/{uid}` — בדיקת נתיב במקום בדיקת תוכן:**

```
allow get:    if canManage(school)
              || (isSignedIn() && uid == memberId());
allow list:   if canManage(school);
allow create: if canRegister(school) && uid == memberId() && ownsIncoming()
              && request.resource.data.approved == false;
allow update: if canManage(school)
              || (isSchoolStudent(school) && uid == memberId()
                  && ownsExisting() && ownsIncoming()
                  && request.resource.data.approved == resource.data.approved);
allow delete: if canManage(school);
```

`create` נשאר על `canRegister` ולא על `isSchoolStudent` — אחרת נוצר מעגל שבו משתמשת חדשה לעולם לא תוכל להירשם. זו הסיבה שבדיקת `approved` היא לב התיקון ולא הקשחה אופציונלית: אילו החברות הייתה *קיום* המסמך בלבד, כל מחובר היה יוצר לעצמו מסמך ב-B בקריאה אחת ונעשה "חבר". `approved` הוא הדבר היחיד בשרשרת שדורש פעולה אקטיבית של המורה (`setStudentApproval`, `app.html:995`).

**ד. שני בלוקי `students`** (מתחת ל-`exam_responses` ול-`homework_responses` — **שניהם**, הכפילות היא עצמה סיכון):

```
allow read:   if canManage(school)
              || (isSchoolStudent(school) && sid == memberId());
allow create: if canManage(school)
              || (isSchoolStudent(school) && sid == memberId() && ownsIncoming()
                  && !request.resource.data.keys().hasAny(['sentToStudent','finalGrade']));
allow update: if canManage(school)
              || (isSchoolStudent(school) && sid == memberId()
                  && ownsExisting() && ownsIncoming()
                  && !request.resource.data.diff(resource.data)
                        .affectedKeys().hasAny(['sentToStudent','finalGrade']));
allow delete: if canManage(school);
```

`resource == null` יורד לגמרי — `sid == memberId()` מכסה גם מסמך שטרם נוצר, בלי לפתוח אורקל אנונימי.

**ה. `activity`** — להחליף `isActiveUser` ב-`isSchoolStudent`.

**ו. אוסף האינדקס החדש — בלוק מבודד, לפני ה-catch-all:**

```
// רמז ניתוב בלבד. לעולם לא מקור הרשאה: slug שנכתב כאן אינו מקנה
// שום גישה — הגישה נגזרת אך ורק מ-schools/{slug}.
match /user_schools/{emailKey} {
  // ההשוואה מול שדה email ולא מול {emailKey}: אי אפשר לשחזר
  // נקודות מתוך קווים תחתונים בשפת החוקים.
  allow get: if isSuperAdmin()
             || (isSignedIn()
                 && resource.data.email.lower() == request.auth.token.email.lower());
  allow list: if isSuperAdmin();
  allow create, update: if isSignedIn()
             && request.resource.data.email.lower() == request.auth.token.email.lower();
  allow delete: if isSuperAdmin();
}
```

`list` חסום לחלוטין — אחרת האוסף הופך לספריית האימיילים של כל התלמידות בכל בתי הספר במקום אחד, ולמנוע אימות "האם כתובת זו רשומה".

**ז.** ה-catch-all `match /{document=**} { allow read, write: if false; }` נשאר בסוף הקובץ ללא שינוי.

## 5. סקריפט המיגרציה ונקודות הרעננות בזמן ריצה

### 5.1 `scripts/build-user-index.js` — התפקיד

עוקב אחר המוסכמות של `scripts/migrate-lamerhav.js` בדיוק:
- **דגל:** `const WRITE = process.argv.includes('--write')` (`migrate-lamerhav.js:17`). בלי הדגל — ספירה והדפסה בלבד, יציאה בשורה המקבילה ל-136.
- **אימות:** להעתיק את `getToken()` ו-`api()` כמות שהם (`migrate-lamerhav.js:25`) — REST מול `firestore.googleapis.com` עם refresh token מה-configstore של firebase-tools. **לא** להכניס תלות ב-`firebase-admin`.
- **כתיבה:** דרך אותו `batchWrite` בנתחי 400, כולל בדיקת הכישלון החלקי (`migrate-lamerhav.js:83`) — `batchWrite` מחזיר 200 גם כשכתיבות בודדות נכשלו. אינדקס חלקי שנראה מוצלח פירושו משתמשת שנחסמת בכניסה מהשורש.

**מקורות הקריאה** — לא `collectionGroup`: אוסף `users` בשורש עדיין קיים, ושאילתה כזו הייתה מחזירה כל מסמך פעמיים ומחייבת פרסינג נתיב. במקום זאת: `listAll('schools')` ואז לכל slug `listAll('schools/'+slug+'/users')` (ה-slug ידוע ודאית), ובנוסף `schools/{slug}.teacherEmail` כשיוך `role: 'teacher'`.

**מפתח:** `email.toLowerCase().trim().replace(/[.@]/g,'_')`. ב-dry-run הסקריפט חייב לדווח על התנגשויות נרמול (שני מסמכי users שמתנרמלים לאותו מפתח) — מצב שדורש הכרעה ידנית, לא כתיבה אוטומטית. הוא גם ידפיס בנפרד כמה אימיילים מופיעים ביותר מבית ספר אחד — זה המספר שמאמת שמודל המערך נכון.

**אידמפוטנטיות:** המזהה דטרמיניסטי, ומערך `schools` נבנה **מחדש מאפס** בכל הרצה ונכתב בדריסה מלאה. **אסור** `arrayUnion` בסקריפט — הוא רק מוסיף, ולכן הרצה שנייה אחרי שתלמידה נמחקה תשאיר שיוך רפאים לנצח. הבנייה-מחדש היא מה שהופך את הסקריפט לכלי תחזוקה ולא לכלי חד-פעמי.

**מצב `--prune`:** מסיר שיוכים לבתי ספר שמסמכם לא קיים (מחיקה ידנית מהקונסול לא מפעילה קוד), ומוחק רשומות שהתרוקנו.

**שלושה אימותים לפני "מתג" ההפעלה** (בדומה ל-`migrate-lamerhav.js:158`, שלא כותב את מסמך המתג אם הספירות לא תואמות ויוצא ב-exit 1):
א. מספר רשומות `user_schools` = מספר האימיילים הייחודיים המנורמלים שנספרו במקור.
ב. הפוך — לכל שיוך ברשומה קיים בפועל `schools/{slug}/users/{safeEmail}` (או `teacherEmail` תואם).
ג. "אף אחת לא נשארה בחוץ" — מעבר על כל מסמכי המשתמשות ווידוא שכל אחת מופיעה.
רק אם שלושתם ✓ מותר לפרוס את שלב 6. כישלון = exit 1, והרצה חוזרת בטוחה.

## 6. רשימת בדיקות

**מקרה התקיפה חוצה-בתי-הספר (הבדיקה החשובה ביותר).** להתחבר כתלמידה מאושרת של בית ספר A, לפתוח DevTools ולהריץ:
```js
await db.collection('schools').doc('B').collection('classes').get();
```
- **לפני שלב 2:** מחזיר את כל תוכנית הלימודים והמבחנים של B. יש לתעד את הפלט כראיה.
- **אחרי שלב 2:** `permission-denied`. לחזור על אותה בדיקה עבור `questions`, `exam_settings`, `notifications`, `media`, `practice` — כל השישה.
- ניסיון כתיבה: `users` create בבית ספר B, `activity` create ב-B, `students` create תחת מבחן של B — כולם חייבים להיחסם.
- **אורקל אנונימי** (בחלון פרטי, ללא התחברות כלל): `get` על `schools/B/exam_responses/{examId}/students/{safeEmail}` — חייב להיחסם, לא להחזיר snapshot ריק. לחזור על אותה בדיקה ב-`homework_responses`.
- **אורקל חברות מחובר:** `get` על מסמך `users` של אימייל אחר ב-B — חייב להיחסם באותה צורה בין מסמך קיים לשאינו קיים.

**רגרסיה של הרשאות לגיטימיות** (`scripts/rules-test.js`, שכבר רץ מול Rules Test API עם functionMocks; יש בו מקרה חוצה-בתי-ספר אחד — "מורה זר קורא מחוון" — וחסר בו מקרה של תלמידה זרה):
- מורה של בית ספר (שאינו המנהל הראשי, ואין לו מסמך `users`) קורא `classes`/`questions`/`media` של בית הספר שלו → ALLOW.
- תלמידה ותיקה של למרחב שמסמכה **חסר** את השדה `approved` → ALLOW (זו הבדיקה שמונעת נעילה המונית).
- תלמידה שטרם אושרה (`approved: false`) → קוראת את המסמך של עצמה, נחסמת מהתוכן, ורואה `PendingApprovalScreen` ולא ספינר תקוע (סדר הרינדור: `app.html:8354` קודם ל-`8366`).
- קריאה עצמית ב-`user_schools` → ALLOW; קריאת רשומה של אחרת → DENY; `list` → DENY.

**מסלול ההרשמה מקצה לקצה (הדרישה "משתמש חדש חייב להצליח להירשם"):** חשבון Google שמעולם לא נרשם, דרך `/school2` — `loadUserProfile` על מסמך שאינו קיים → `StudentNameScreen` → `saveUserProfile` עם `approved:false` → `PendingApprovalScreen` → המורה מאשרת → רענון → תוכן נטען. לוודא שנוצרה רשומת `user_schools`.

**זהות מסך הכניסה:** צילומי מסך של `/lamerhav`, `/school2` ו-`/app.html` — אותו טקסט, אותו לוגו, אותן כרטיסיות, ואותו מסך ראשון בטעינה. בנוסף `/slug-שלא-קיים`: אין slug על המסך; `/slug-מושהה`: אין שם בית ספר. חיפוש טקסטואלי ב-DevTools אחרי שם בית הספר בעמוד שלפני ההתחברות — אפס תוצאות.

**תרחישי אינדקס וניתוב (שלב 6):** שיוך יחיד → הפניה ל-`/{slug}`; שני שיוכים → מסך בחירה עם סימון "מושהה"; אפס שיוכים → מסך "בקשי קישור"; slug באינדקס שמסמכו נמחק ידנית → מסונן, לא מסך שבור; מורה של בית ספר חדש וריק (בלי אף `users`) → מנותב נכון.

**רגרסיה של מצב:** `enterDemo` מכל כתובת; טיימר מבחן — לפתוח מבחן, לרענן, לוודא שזמן ההתחלה נשמר (`lsKey`, `app.html:8081/8095/9391`); `isEditor` נקבע נכון למורה שאינה המנהל הראשי; קריאות AI מיוחסות ל-slug הנכון ב-Worker.

## 7. סיכונים פתוחים

1. **`firestore.rules` נערך במקביל לבדיקה.** בקובץ העבודה כבר יש תיקון חלקי (`isMember` על `exists()` בלבד), וגרסת HEAD שונה ממנו. אחת האזהרות מציינת שבגרסת ביניים `users create` דרש `isActiveUser` שכבר דרש חברות — כלומר **הרשמה חדשה נחסמה**. חובה לקרוא את הקובץ הנוכחי, להריץ את מסלול ההרשמה מקצה לקצה, ולא להסתמך על אף מספר שורה בסעיף 1.
2. **המעגל בהרשמה.** אם `create` על `users` יוקשח בטעות ל-`isSchoolStudent`, אף אחת לא תוכל להירשם שוב — כשל שקט לחלוטין. זו השורה הרגישה ביותר בכל התוכנית.
3. **הכפלת עלות הקריאה.** כל בקשה תשלם היום קריאת `schoolDoc` אחת ותשלם שתיים אחרי התיקון (2 נתיבים; המגבלה היא 10 get/exists לבקשה ו-20 לשאילתה — אנחנו ב-2). זניח כספית, אבל Blaze אינו כולל תקרת הוצאה אלא התראה בלבד (`docs/blaze-checklist.md` §6) — להגדיר התראת תקציב **לפני** הפריסה. (הנתון "50,000 קריאות ליום" שהוזכר בבדיקה אינו מתועד בריפו ואינו מאומת.)
4. **`approved` כמקור אמת יחיד.** אם מישהו יכתוב `approved: true` ישיר בחוקים במקום `.get('approved', true)`, כל תלמידה ותיקה של למרחב תינעל — כשל שייראה כ"החוקים שברו את האתר".
5. **שבירת סימניות של השורש.** הסרת ה-redirect `/ → /lamerhav` (`vercel.json:5`, `firebase.json:19`) משנה את מה שרואות תלמידות שסימנו את השורש. לכן שלב 6 אחרון, ורק אחרי שלושת האימותים.
6. **התיישנות האינדקס.** מחיקת בית ספר נעשית ידנית מהקונסול ואינה מפעילה קוד; מחיקת תלמידה מטופלת רק בנקודה 2. הקורא חייב להיות סובלני, ו-`--prune` חייב לרוץ תקופתית.
7. **שני עצי נתונים במקביל.** עד שלב 3 השורש חי; משתמשת יכולה "להתקיים" בשני מקומות והאינדקס ממפה רק אחד. אם מדלגים על שלב 3, האינדקס עלול לשקר בשקט.
8. **באג קיים שאינו חלק מהשינוי:** `loadPlatformLessons` (`app.html:7323`) עם deps `[]` — במסלול של התחברות טרייה `signInWithPopup` (`app.html:7651`) אינו טוען מחדש את הדף ו-`App` אינו מתמונט, ולכן `globalLessons` נשאר `{}` עד סוף הסשן. ראוי לתיקון נפרד; שלב 6, שמבצע ניווט מלא, דווקא מנטרל אותו במסלול השורש.
9. **דליפה שיורית שאינה נסגרת:** `schools/{school}` נשאר `allow get: if true` (המסך שלפני ההתחברות זקוק לו), ולכן slug מנוחש עדיין חושף `name` ו-`teacherEmail`. הסתרת השם ב-UI אינה הופכת אותו לסודי — ההגנה על הקריאה חייבת לעמוד בפני עצמה ולא להישען על סודיות ה-slug.
10. **`RESERVED_SLUGS`.** `/admin`, `/login`, `/docs` נתפסים ב-rewrite ומגיעים ל-`app.html` במצב legacy (`app.html:523`, `12808`) — כלומר מציגים היום את אוספי השורש של למרחב. שווה לסגור ממילא; אחרי שלב 3 הם יציגו מסך ריק במקום תוכן.
